# Decision log

Short, dated records of choices made while building PitchLens, newest last.

| # | Decision | Why | Scoring axis |
|---|----------|-----|--------------|
| D1 | **The test clip `vizuals_test.mp4` was not available in the build environment** (only the reference image arrived, as a chat attachment). The rights-clear *synthetic broadcast footage generator* (planned for Phase 7) was moved to Phase 3 and became the primary development substrate. All vision code stays source-agnostic and accepts any clip via `--video`; see `docs/REAL_CLIPS.md`. | Keeps the build unblocked, and synthetic footage has *known ground-truth cameras*, which turns homography accuracy into a measurable test instead of an eyeball check. | Tech, UX, compliance |
| D2 | Name: **PitchLens**. Fictional clubs **Kestrel Bay FC (KBY)**, crimson/navy, and **Ironvale Athletic (IRV)**, white/teal. Demo protagonist: **#7 Jory Kestane** (KBY, "pressing playmaker"). | All marks are invented; colours mirror the red-vs-white contrast of the reference footage. | Compliance |
| D3 | Python 3.11+ (developed on 3.13), pydantic v2 contracts, FastAPI, OpenCV/NumPy. Plain HTML/JS web UI instead of React. | No build step, fastest iteration; the canvas renderer is ~1 file. | UX, maintainability |
| D4 | The simulator is **agent-based at 10 Hz** (players chase tactical targets; possession state machine), not an event-only Markov chain. | One simulation yields consistent events *and* tracking, so speeds, sprints, pressure and video alignment all agree. | Dataset innovation |
| D5 | Narrative "scripts" only nudge conversion of decent chances (xG >= 0.08) inside time windows. They never inject goals out of nowhere. | Storylines (late comeback, etc.) happen reliably, while the data still looks like football. | Dataset realism |
| D6 | Demo match: `seed=6, narrative=late_comeback` (re-picked after the D14 realism pass). IRV lead 1-0 (22'), KBY level (40') and win it at 89:11. Demo clip 62:01-62:31: #7 Kestane's 3rd attacking-third interception (62:11). One of the three came in the first half, so it exercises the D12 orientation flip. | Realistic counts (2-3 high interceptions for a pressing 10), a late winner, and a spatial story. | Real-world impact, UX |
| D7 | Pitch lines in the synthetic footage are drawn as projected ground-plane quads (real 12 cm width), not warped texture. | Perspective-correct, anti-aliased lines at every depth; no texture minification shimmer. | UX |
| D8 | The overlay timeline is renderer-agnostic JSON on the *media clock*, with pitch-space geometry. Camera (homography) and player screen tracks are separate streams. | The engine, the camera solver and the renderer can each be swapped (e.g. a broadcaster's own graphics engine). | Tech, impact |
| D9 | Registration uses **chamfer refinement**: 4 image-anchor offsets optimised with robust least squares over the truncated line distance transform. ICP-style nearest-point snapping was dropped. | Nearest-point ICP suffered from the aperture problem along long lines and made drift *worse*. Chamfer brought 30 s error to 1.1 px mean / 2.8 px max at 1080p. | Tech |
| D10 | The tracker associates detections in **pitch space** (foot point through H^-1), not image space. | Camera pans of up to ~340 px/s dominated image-space motion. Pitch-space association halved track fragmentation (8.1 -> 3.9 tracks per player). | Tech |
| D11 | Identity comes from Hungarian matching of track pitch positions against the dataset's tracking, plus a majority vote per track. Real clips use a user-provided anchor map. | Fragmented tracks still resolve to the right player (94.7% of matched boxes), so the player highlight is robust. | Tech, UX |
| D12 | Evidence from the other half is rotated 180 degrees into the current attacking direction. | Teams swap ends, so a raw "4 interceptions in attacking third" would otherwise be spread over both goals. This is the usual broadcast convention, and the analyst caption says so. | UX, explainability |
| D13 | The ball detector masks projected pitch lines and the goal volume via the homography. | Line fragments and goal-net mesh caused about 97% of false positives. | Tech |
| D14 | **Realism pass on the simulator**: higher pass completion (~78-80%), interceptions require a tight passing lane, tackle attempts halved, xG and shot appetite recalibrated. Player *anticipation* (pressing x vision) widens interception reach, which is how a pressing playmaker stands out. | Analysts judge plausibility. Shots (~10-20 per team), xG (~0.6-2.6) and pass volumes are now in a realistic range. Interception counts stay above elite-league averages (see DATA_CARD limitations). | Dataset realism |
| D15 | The Verifier uses word-boundary superlative matching plus a short whitelist of methodology constants (5/10-minute windows, the 25 km/h sprint threshold). | Substring matching flagged German *bestimmt* as "best". The constants are definitions, not claims. | Explainability |
| D16 | The Director can **preempt**: a card that has been on air for >= 4 s can be cut for a candidate scoring >= 1.35x, and its graphics animate out. | Without it, a mid-value card would block the moment that matters (seen in the demo clip). Human directors cut to the bigger story. | Agentic design, UX |
| D17 | The own-third interceptions detector is off by default. | The simulator counts every cut-out pass as an interception, so deep counts (15+) look implausible. Attacking-third counts (2-3) are realistic. | Dataset realism |
| D18 | PPDA uses the standard denominator (tackles, interceptions, fouls; no loose-ball recoveries), and long windows scan the full event history. | It fixed PPDA ~1 -> 6.8 vs 10.5, and the pressing-surge detector now compares against the true match baseline. | Correctness |
| D19 | The demo bundle ships a VP9 copy of the footage, which the web player uses when H.264 is unavailable. | Open-source Chromium (used for automated UI capture) has no H.264 decoder. | UX, reproducibility |
| D20 | The real development clip arrived via a GitHub upload to the public branch. It was copied to the git-ignored `data/test_assets/` and **removed from the branch tip**. Purging it from history needs a force-push, which waits for the owner's go-ahead. | Brief section 9: third-party footage must not be in the public repo. | Compliance |
| D21 | Real-clip registration: whole-image flow features, paint-preserving player mask, and per-frame best-candidate selection across keyframe passes. 5 manual keyframes for the 30 s clip. | Leave-one-out showed the nearest-keyframe rule failing (217 px) where another pass was fine (3 px). The changes also improved synthetic accuracy (2.0 -> 0.9 px). | Tech |
| D22 | Synthetic-on-real alignment = clock offset + attack orientation + retargeting the anchored player's in-clip events. Retargeted points are labelled. | Meets the brief's "events line up with positions visible in the footage" without pretending the vision data is ground truth. | Tech, honesty |
| D23 | The primary product is now a **producer workflow**: event data only, an analyst agent proposes outstanding player insights, a human approves each one before it airs (`/producer` console, `/onair` browser source). The automatic video-overlay pipeline stays as an R&D track. | Matches how live TV works: an editor owns what goes on air. Event-only input runs on any feed (no video, tracking or calibration). Approval is the safety net for an AI on a live broadcast. | Product, safety |
| D24 | The analyst is selective by rule: rank 1 or 60%+ of the team's total, per-metric value bars, at most 2 proposals per player and stat, at least 75 s between proposals, 150 s time-to-live. Over the demo match that is **7 proposals in 90 minutes** (the scout alone fires ~110 player insights). | A producer can review one card every ~13 minutes; a flood would be ignored or rubber-stamped. | Product |
| D25 | Operator edits go through the same Verifier as the agent's text (live check while typing). An edit with a number or name that is not in the evidence cannot be approved. | Human-in-the-loop must not become a back door around grounding. | Safety, honesty |
| D26 | The on-air graphics are one shared component (`web/broadcast/card.js` + `card.css`): the console preview and the program output render the same code, so what the producer approves is pixel-for-pixel what airs. Visual identity is an original "top-flight" theme (no real league marks, names, fonts or colours). | WYSIWYG approval; compliance with the brief's trademark rules. | UX, compliance |
